## 4. 异常行为模式

### 4.1 audit 失败被静默视为通过

- **触发条件**: `AuditAgent.audit` 抛错（基础设施异常）或 `AuditAgent.auditWorld` 抛错
- **影响**:
  - `coordinator-service.ts:262-267`: audit 抛错 → return null → executeAgent 视为 audit 通过 → 子 Agent 结果被接受
  - `AgentRuntime.ts:3301-3306`: auditWorld 抛错 → auditResult undefined → reviewStoryConsistency 返回的 decision 无 auditResult → post-react 跳过 audit-based repair
  - `AgentRuntime.ts:3426-3431`: init 路径同样模式
- **后果**: 审计基础设施故障时，所有数据完整性问题被掩盖，违反 §13.3"错误数据必须暴露"

### 4.2 EntityGraphRepairer 自动创建空 boundary 掩盖 GM 缺陷

- **触发条件**: GM 未调用 `upsert_boundary` 初始化实体信息边界，实体参与写操作触发 audit
- **影响**:
  - `EntityGraphAuditor.ts:285`: 生成 `severity: 'medium'` issue
  - `GraphConsistencyChecker` (line 150): medium → warning
  - `EntityGraphRepairer.ts:187-198`: 自动创建 `known_facts=[], unknown_facts=[]` 的空 boundary
  - 下次审计时 `boundary.unknownFacts.length === 0`（line 289），越界检测永远不触发
- **后果**: GM 未初始化 boundary 的缺陷被自动修复掩盖，后续信息边界泄漏无法被检测

### 4.3 auditWorld 的 rootCause 硬编码

- **触发条件**: 调用 `AuditAgent.auditWorld`
- **影响**: `AuditAgent.ts:91`: `rootCause: programFailures.length > 0 ? 'data_missing' : undefined`，跳过 `rootCauseClassifier.classify`
- **后果**: 所有 auditWorld 失败被归类为 `data_missing`，无法区分 context_injection_error / llm_understanding_error / tool_execution_failure，影响修复策略选择

### 4.4 init/chat repair 循环收敛条件不一致

- **触发条件**: post-react repair 执行
- **影响**:
  - chat 路径（line 2783）: `postReactResult.requiresRepair`（由 storyPostReactPipeline 基于 repairReasons 计算）
  - init 路径（line 2888-2892）: `postReviewDecision?.auditResult && !postReviewDecision.auditResult.pass`
  - chat 路径的 repairReasons 包含 todo/pacing/second_layer 等多种原因，init 路径仅基于 auditResult.pass
- **后果**: 两条路径的修复触发条件不对称，可能导致 init 路径过度修复（仅 audit 失败即修复）或 chat 路径修复不足（audit 通过但 todo 未完成也修复）

### 4.5 spawn_agent 与 batch_spawn_agents 的 fallback 模式重复

- **触发条件**: agentRegistry 未设置或 agent 未注册
- **影响**:
  - `coordinator-service.ts:431-436`（spawn_agent）和 `631-655`（batch_spawn_agents）均调用 `buildMissingAgentFallback`
  - 但 spawn_agent 在 agent 未找到时返回 `success: true` + fallback（line 439-444），而 batch_spawn_agents 在 agent 未找到时返回 `success: true` + fallback（line 710-716）
  - 两处的 fallback 语义一致但代码重复
- **后果**: 修改 fallback 行为需同步两处

## 关键结论

1. **AgentRuntime 是核心瓶颈**：3588 行 God class，承担 ≥10 个独立职责，是审查修复子系统的单点复杂度来源。init/chat 两条路径的 repair 循环重复（问题 #2）和 review 方法重复（问题 #3）均源于此类未拆分。

2. **审查修复的"fallback 掩盖缺陷"模式普遍存在**：问题 #4（auditWorld dummyRequest）、问题 #5（severity 降级）、问题 #7（audit 失败视为通过）、问题 #8（空 boundary 自动修复）均违反用户规则"fallback是掩盖主逻辑缺陷的低级做法"和架构规范 §13.3"错误数据必须暴露"。

3. **EntityGraphAuditor 与 EntityGraphRepairer 之间缺乏结构化契约**：问题 #9 的字符串模式匹配是典型抽象泄漏，Auditor 生成的字符串描述被 Repairer 反向解析，任何一方修改描述格式都会静默破坏另一方。

4. **coordinator-service.batch_spawn_agents 与 AgentRuntime 同病**：两者都是 God function/class，承担过多职责，且内部包含重复的 fallback 模式（问题 #6、问题 #10）。

## 4. 异常行为模式

### 4.1 warning severity 触发 repair 循环

- **触发条件**: AuditFailure.severity === 'warning'（来自 GraphConsistencyChecker 的 medium issue 或 InfoBoundaryChecker）
- **影响**:
  1. AuditAgent.audit 返回 `pass: false`

  3. flushWithAudit 阻断 flush，throw Error

- **触发条件**: coordinator-service 批量调度中，子 Agent A audit 失败，子 Agent B 开始执行

  1. A 的 staging writes 残留在共享 stagingPool

  3. 脏写入最终 flush 到 DB
- **根因**: audit 失败路径无 stagingPool 清理

### 4.3 EntityGraphRepairer regex 匹配失败静默跳过

- **触发条件**: EntityGraphAuditor 修改 issue.proposedChange 或 currentRelation 的字符串格式
- **影响**:
  1. EntityGraphRepairer.repairIssue 匹配失败，返回 false
  2. 修复循环认为"无法修复"，提前终止
  3. 未修复的 issues 阻断 flush
- **根因**: Auditor 与 Repairer 之间是隐式字符串契约，无类型保障

### 4.4 auditWorld 对 EntityCountsChecker 隐式跳过

- **触发条件**: AuditAgent.auditWorld 创建 dummy request 无 expected.counts
- **影响**: EntityCountsChecker 返回空数组，世界级审核不检查实体数量

## 2. 问题清单

### P1：repair 循环每轮创建新 stagingPool，前一轮修复写入被丢弃（Critical）
- **位置**：`AgentRuntime.ts:2786`、`AgentRuntime.ts:2834-2836`
- **问题类型**：状态机缺陷 + 数据流转断裂
- **严重程度**：Critical
- **置信度**：Confirmed
- **优先级矩阵**：影响 高 × 紧急度 立即
- **代码证据**：

- **状态转移路径**：
  - 第 1 轮：`post_react` → `repair`（新建 stagingPool_1）→ `post_react`（仍 requiresRepair=true）→ stagingPool_1 被覆盖丢弃
  - 第 2 轮：`repair`（新建 stagingPool_2，从 DB 重拍快照，看不到 stagingPool_1 的修复）→ `post_react`
- **影响**：第 1 轮的修复工作完全浪费，第 2 轮基于原始状态重做。修复循环非增量，效率低且可能因"重复修复"产生冲突。`createRepairRuntime` 内部 `shadowState.ensureSnapshot()` 从 DB 重新拍快照（AgentRuntime.ts:3003），看不到前一轮 stagingPool 的写入。

- **关联规则**：违反 institution.md 核心原则 8（禁止 fallback 掩盖主逻辑缺陷）——retry 本质是 fallback，但未清理脏数据导致 fallback 无效。

## 3. 性能优化潜力点

### 3.1 修复循环可改为增量模式（可量化）
- **当前**：每轮创建新 stagingPool + `shadowState.ensureSnapshot()` 从 DB 重拍快照（AgentRuntime.ts:3003）。每次快照涉及多张表全量读取。
- **优化**：修复循环共享 stagingPool，前一轮的写入对下一轮可见。
- **预期收益**：减少 N-1 次 `ensureSnapshot` DB 查询（N=修复轮数，当前 N=2，未来可能增加）；减少 N-1 次重复修复写入。

### 3.2 EntityGraph audit 可增量审计（可量化）
- **当前**：`flushWithAudit` 每轮 `auditStagedWrites` 遍历所有 staging writes（EntityGraphAuditor.ts:27-44），复杂度 O(writes)。
- **优化**：修复后只审计修复写入涉及的节点/边，而非全量重审。
- **预期收益**：每轮审计从 O(writes) 降到 O(repair_writes)，在 writes 数量大时收益显著。

### 3.3 子 Agent audit retry 前清理 staging writes（可量化）
- **当前**：retry 时前一轮写入累积，audit 必然失败（P3）。
- **优化**：retry 前 `stagingPool.rollbackFrom(snapshotIndex)` 回滚到子 Agent 执行前。
- **预期收益**：重试实际有机会成功，避免浪费 retry_budget。

## 4. 异常行为模式

### 4.1 "修复循环假收敛"模式
- **触发条件**：第 1 轮修复解决了部分问题（requiresRepair 从 true→false），但第 2 轮 review 基于第 1 轮的 stagingPool 评估时，因 P1（stagingPool 隔离）看不到第 1 轮修复。
- **实际行为**：第 2 轮 review 看到原始问题，requiresRepair 仍 true，循环退出抛错。
- **影响**：实际已部分修复的写入被丢弃（孤儿 stagingPool），用户看到"修复失败"但部分工作已完成。

### 4.2 "审核静默放行"模式
- **触发条件**：`AuditAgent.audit` 抛异常（如 DB 查询失败、ShadowState 损坏）。
- **实际行为**：coordinator-service.ts:262-267 吞错当作 pass，子 Agent 的脏数据被合并到主 stagingPool。
- **影响**：错误数据落库，后续请求基于错误数据运行，问题被推迟到 EntityGraph audit 阶段（flushWithAudit），但那时已无法回溯到子 Agent。

### 4.3 "reconcile 计数器漂移"模式
- **触发条件**：P6——flushWithAudit 失败时 `lastRequestWriteCount` 未重置。
- **实际行为**：下次成功请求的 reconcile 计数 = 旧值 + 新值，可能过早触发 reconcile。
- **影响**：reconcile 在不适当的时机运行，可能基于不完整状态产生错误修复。

### 4.4 "修复写入污染 audit"模式
- **触发条件**：EntityGraph repair 写入通过 `stagingPool.stage()` 添加（EntityGraphRepairer.ts:286），但修复写入本身可能引入新问题（如重复边）。
- **实际行为**：下一轮 `auditStagedWrites` 把修复写入也纳入审计范围，可能发现修复引入的新问题，导致修复循环无法收敛。
- **影响**：修复循环 2 轮后抛错，stagingPool 的所有 writes（含修复写入）被丢弃（flushWithAudit 抛错，主 stagingPool 未 clear 但 finalResponse.success=false）。

## 7. 总结

审查修复子系统存在 **3 个 Critical** 问题（P1/P3/P5）和 **2 个 High** 问题（P2/P4），核心问题集中在：

1. **修复循环的 stagingPool 隔离设计**（P1）导致修复工作被丢弃，是最大的架构缺陷
2. **子 Agent audit retry 不清理 staging writes**（P3）导致重试注定失败
3. **audit 异常被静默吞掉**（P5）违反"程序错误不可包容"原则

这 3 个 Critical 问题相互关联：P1 导致修复循环效率低下，P3 导致子 Agent 重试无效，P5 导致审核失效——三者共同导致"审查修复子系统"在异常路径下基本失效，无法达成设计目标。

按优先级建议处理顺序：P3 → P5 → P1 → P2 → P4 → P6 → P7 → P8。

## 4. 异常行为模式

### 4.1 子 Agent 审核抛异常 → 静默通过

- **触发条件**: `AuditAgent.audit` 内任意 checker 抛错（如 `GraphConsistencyChecker.check` 调 `auditStagedWrites` 时 `graphProvider.getEdges` 异常）
- **影响**: 子 Agent 错误数据被采纳，GM 基于错误数据推进剧情
- **位置**: `coordinator-service.ts:262-267`

### 4.2 子 Agent 审核失败 → staging writes 累积

- **触发条件**: 子 Agent 第 1 轮审核失败，retry_budget > 0，递归重试
- **影响**: 重试时旧 writes 仍在 stagingPool，新 writes 叠加，审核必然再失败，retry 预算白白耗尽；最终 stagingPool 中残留错误 writes
- **位置**: `coordinator-service.ts:891-900`

### 4.3 init 路径后审 LLM 与程序审脱节

- **触发条件**: `reviewInitConvergence` 调 `auditWorld`，但 dummyRequest 让 `EntityCountsChecker` 静默跳过
- **影响**: 资源数量校验只靠 LLM review 判断（prompt 提示"全部资源达到最小阈值"），程序审维度形同虚设；LLM 判断不稳定时可能放过数量不足的初始化
- **位置**: `AuditAgent.ts:79-84`、`program-checkers/index.ts:13-14`

### 4.4 auditWorld rootCause 错误归因

- **触发条件**: auditWorld 检测到任何维度失败
- **影响**: 强制设为 `data_missing`，GM 修复方向被误导为"检查数据层"，而实际可能是图关系一致性、信息边界违规等
- **位置**: `AuditAgent.ts:91-92`

### 4.5 warning 级失败触发完整 GM repair

- **触发条件**: `InfoBoundaryChecker` 标 `warning` 的 npc→quest knows 检测命中
- **影响**: 触发完整 GM repair 循环（1 轮 LLM ReAct + 重审），浪费资源；GM 修复方向可能反而引入新问题
- **位置**: `AuditAgent.ts:89`、`StoryPostReactPipeline.ts:163`

3. **repairExecutor 调用 executeReActWithRecovery 启动第二次 GM agent，形成 GM→audit→repair→GM 循环** — **✅ 已确认存在，但有界**（问题 #9）。双层防护：`repairRoundCount < 2`（post-react）+ `MAX_REPAIR_ROUNDS = 2`（flushWithAudit）+ `MAX_AGENT_DEPTH = 1`（coordinator 递归深度）。无无限循环风险，但单次 chat 请求最坏可触发 6+ 次 auditStagedWrites（问题 #8）。

## 关键发现总结

1. **3 处 fallback 掩盖缺陷**：audit 异常静默通过（问题 #2）、retry 不清理 writes（问题 #3）、dummyRequest 让 EntityCountsChecker 静默跳过（问题 #6）—— 均违反用户规则"fallback是掩盖主逻辑缺陷的低级做法"。

2. **2 处重复实现**：InfoBoundaryChecker vs auditInformationBoundary（问题 #4）、auditWorld 与 flushWithAudit 重复审计（问题 #8）—— 违反 code-standards 第二章第4条"一个概念只表达一次"。

3. **1 处死代码**：auditGraphState 已定义但无调用（问题 #5）—— 违反 code-standards 第二章第3条"删代码比加代码更有价值"。

4. **2 处根因误导**：auditWorld 硬编码 rootCause='data_missing'（问题 #7）、warning 级失败触发完整 repair（问题 #1）—— 导致 GM 修复方向错误。

5. **关键调用链未断裂**：所有审计入口（auditWorld/audit/auditStagedWrites）均有完整调用链至最终修复或抛错，无接口断路。但 `auditWorld` 的 dummyRequest 让 `EntityCountsChecker` 形同虚设，属"链路通但语义断"。

6. **跨层直调合规**：所有跨层调用均通过端口接口注入（IAuditAgent / IEntityGraphAuditor / IEntityGraphRepairer / IEntityGraphReconciler），未发现违反 7 项禁止依赖的直调。

## 设计呈现 — Section 1：审核流程架构

[触发 on_task_complete hook（携带 saveId, stagingPool, agentType）]
       ↓

       ↓
[AuditAgent 生成 AuditReport]
       ↓
[报告通过 hook patch 返回给原 Agent]
       ↓
[原 Agent 阅读报告]
      ├─ 有 issues → Agent 自行修复（继续 ReAct iteration）→ 任务结束
      └─ 无 issues → 任务结束
       ↓
[不再触发第二轮审核（一个任务仅报告一轮）]

**关键设计点**：

1. **统一审核节点**：GM agent 和子 Agent 任务完成时都走相同流程
2. **"即将完成"而非"已完成"**：Agent ReAct loop 想要终止时触发审核，如果报告有问题，Agent 可以继续 iteration 修复
3. **仅一轮**：审核只做一次，Agent 修复后不再二次审核，由定期 reconcile 兜底
4. **AuditAgent 纯无状态**：只接受 `saveId + stagingPool`，返回 `AuditReport`，不触发任何修复
5. **报告返回原 Agent**：通过 hook 的 patch 机制注入到 Agent 的 context
