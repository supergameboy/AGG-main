```

  战斗进行  → TurnBasedCombatStrategy 内部纯代码"敌人 AI 决策"

用户期望：
  战斗开始  → GM Agent 判定 + Combat Agent 输出敌人策略（一次性策略决策）
  战斗进行  → 程序基于 Combat Agent 输出的策略自动处理每回合
```

**偏差 2：完整的 task 通过 message 字段传递，不在 system prompt 中**

**影响**:

**建议修复方案**:

在 [system-design §2.1.1](file:///c:/Users/super/Documents/trae_projects/AGG-main/docs/design/fractal-design-20260723-game-combat-mode-separation/system-design-20260723-game-combat-mode-separation.md#L226) 注入路径 1 表格"实现机制"列补充完整传递路径：

### P1-1 parseChallengeAction 使用 `as unknown as` 双重断言

**优先级**: P1
**位置**: [game-service.ts L930-931, L938-939](file:///c:/Users/super/Documents/trae_projects/AGG-main/packages/backend/src/services/game-service.ts#L930-L939)

```typescript
if (explicit && typeof explicit === 'object' && typeof explicit.type === 'string' && typeof explicit.actorId === 'string') {
```

### P1-2 CombatService 内存缓存与 ShadowState 职责重叠

**优先级**: P1
**位置**: [CombatService.ts L93](file:///c:/Users/super/Documents/trae_projects/AGG-main/packages/backend/src/game-systems/combat/CombatService.ts#L93) `combatStateCache: Map<ID, CombatState>`、[CombatService.ts L524-525](file:///c:/Users/super/Documents/trae_projects/AGG-main/packages/backend/src/game-systems/combat/CombatService.ts#L524-L525) `getCachedState` 优先读缓存
**违反规则**: architecture-standards 第九章"数据层多重暂存/隔离机制禁止混淆" + code-standards 第八章"单一数据源"

**问题分析**:
- G2 路径 `executeStepOnly` → `getCombatState` 先查内存缓存 `combatStateCache`
- 若缓存命中，直接返回内存对象，**不查 StagingKnex 代理 → 不查 ShadowState → 不查 DB**
- ShadowState 已注册 combat_states 表（P-5 证据），本应成为同请求内读写的单一数据源
- 内存缓存的存在掩盖了 ShadowState 的作用，形成两套缓存机制

**当前为何未暴露 bug**: G2 路径每请求通过 `requestScope.getOrCompute('combat', ...)` 创建新 CombatService 实例，缓存不跨请求。同请求内 `executeStepOnly` 写缓存 → `checkEnd` 读缓存，逻辑上正确。但这是"碰巧正确"，而非"设计上正确"。

**风险**: 若未来 CombatService 被错误提升为跨请求单例，缓存会返回陈旧数据，ShadowState 无法感知。

**修复建议**: 移除 `combatStateCache`，统一依赖 ShadowState（StagingKnex 代理读操作已先查 ShadowState）。或显式标注缓存仅为"同请求内避免重复 DB 查询"的优化，并添加请求边界清理断言。

### P1-4 handleProgramAction 失败时 flush 落盘脏数据

**优先级**: P1
**位置**: [game-service.ts L760-775](file:///c:/Users/super/Documents/trae_projects/AGG-main/packages/backend/src/services/game-service.ts#L760-L775)
**违反规则**: code-standards 第六章第2条"错误处理恰当，让问题尽早暴露"

**问题分析**:
```typescript
} catch (error) {
  // 返回 G2_ORCHESTRATION_FAILED 错误
  return { success: false, errorCode: 'G2_ORCHESTRATION_FAILED', ... };
} finally {
  // 无论成功失败，都 flush
  await coordinatorAgent.flushRequestRuntime(requestRuntime);
}
```
- 若 `orchestrator.executeStep` 部分执行后抛错（如 `executeTurnForOrchestrator` 成功写入 combat_states，但 `checkChallengeEnd` 抛错），StagingPool 中已有部分写入
- `finally` 仍会 `flushRequestRuntime`，将部分写入落盘 DB，产生**脏数据**
- 战斗状态可能处于不一致的中间态（如回合已推进但未检测结束）

**修复建议**: catch 块中应显式 `requestRuntime.stagingPool.clear()` 或标记为"不 flush"，仅成功路径才 flush。或改为：
```typescript
try {
  const result = await orchestrator.executeStep(...);
  // ... 成功处理
  return ...;
```

## 不同游戏类型变体的应对能力分析

- text_rpg：回合制规则（物品使用消耗一个回合）
- rpg_2d：实时规则（物品有冷却时间）

### 2. 技能差异（character_skills 数据）— ✅ 当前已支持

- 技能是**角色数据**（character_skills 表），与 Agent 实例无关
- SkillService 通过 `saveId` 查询当前角色的技能

```
  ├─ 3. 检查挑战结束（路由编排）
  └─ 4. routeToAgent 判定（路由编排）

      └─ false → flush + 返回数值结果

  └─ ChallengeProgram
      └─ executeTurn(saveId, action, context) → ChallengeStepResult
          （只做程序性执行，不做状态查询/结束检测/路由判定）
```

### 关于独立编排层
